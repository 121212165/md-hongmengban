# hongmengMD 多格式转换插件设计

## 1. 文档目的

- 明确 `hongmengMD` 中“多格式导入导出”能力的技术边界。
- 统一格式转换模块的职责、接口和落地方式。
- 为 `0.0.2` 阶段的导入导出实现提供工程设计依据。

## 2. 结论先行

当前阶段最合适的不是做一个完整的第三方插件生态，而是做一个应用内独立的格式转换插件模块。

这个模块负责：

- 识别输入格式
- 读取输入内容
- 转换为 Markdown
- 从 Markdown 导出目标格式

主应用负责：

- 文件选择
- 工作区管理
- 文档管理
- 编辑与预览
- 导出和分享流程调度

## 3. 设计原则

### 3.1 Markdown 是唯一内部标准格式

所有导入能力都应先转换为 Markdown，再进入编辑器和存储层。

所有导出能力都从 Markdown 出发生成目标格式。

核心闭环：

`外部格式 -> Markdown -> 编辑 / 保存 -> Markdown -> 外部格式`

### 3.2 不做多格式互相直转

不设计：

- `txt -> html`
- `html -> pdf`
- `docx -> txt`

统一通过 Markdown 中转，避免转换矩阵膨胀。

### 3.3 先做最小可用，再扩展格式

`0.0.2` 只实现：

- Markdown 导入
- Text 导入
- Markdown 导出
- Text 导出

复杂格式如 `pdf`、`html`、`docx` 不进入首批必做范围。

### 3.4 插件模块必须可测试

每个格式转换器必须独立可测，不能把解析逻辑埋进页面代码或 `FileService`。

## 4. 插件模块定位

## 4.1 这是“模块化插件”，不是“插件市场”

当前版本中的“插件”含义是：

- 独立目录
- 独立接口
- 独立导入器
- 独立导出器

不是：

- 动态热插拔
- 第三方外部安装
- 在线插件市场

## 4.2 模块职责边界

插件模块负责：

- 文件类型识别
- 内容读取后的解析
- 转换结果标准化
- 导出内容生成

插件模块不负责：

- 页面导航
- 工作区切换
- 当前文档状态
- 文件选择器 UI
- 导出后系统分享

## 5. 架构设计

## 5.1 推荐目录结构

建议在 `entry/src/main/ets` 下新增：

```text
format-plugin/
  types/
  detector/
  importer/
  exporter/
  converter/
  tests/
```

建议对应职责：

- `types`
  - 定义输入输出接口
- `detector`
  - 识别文件类型
- `importer`
  - 各类导入器
- `exporter`
  - 各类导出器
- `converter`
  - 通用 Markdown 转换工具
- `tests`
  - 转换器测试样本与测试代码

## 5.2 与主应用的关系

主应用调用链建议为：

`文件选择 -> ImportService -> FormatPlugin -> Markdown -> FileService -> 编辑器`

导出链建议为：

`当前文档 Markdown -> ExportService -> FormatPlugin -> 文件落盘 -> 分享`

## 6. 输入输出标准

## 6.1 导入输入对象

建议定义统一输入：

```ts
interface ImportSource {
  fileName: string
  filePath?: string
  extension: string
  mimeType?: string
  textContent?: string
  binaryContent?: Uint8Array
}
```

说明：

- 文本类输入优先使用 `textContent`
- 二进制类输入使用 `binaryContent`
- `filePath` 可选，避免插件和文件系统深耦合

## 6.2 导入输出对象

建议定义统一输出：

```ts
interface ImportResult {
  title: string
  markdown: string
  sourceType: string
  warnings: string[]
}
```

说明：

- `title` 用于初始化文档标题
- `markdown` 是唯一标准结果
- `warnings` 用于提醒低保真转换

## 6.3 导出输入对象

```ts
interface ExportSource {
  title: string
  markdown: string
}
```

## 6.4 导出输出对象

```ts
interface ExportResult {
  fileName: string
  mimeType: string
  textContent?: string
  binaryContent?: Uint8Array
  warnings: string[]
}
```

说明：

- 文本格式导出用 `textContent`
- 二进制格式导出用 `binaryContent`

## 7. 核心接口设计

## 7.1 文件类型识别器

```ts
interface FormatDetector {
  detect(fileName: string, mimeType?: string): string | null
}
```

职责：

- 根据扩展名和 MIME 判断文件类型

## 7.2 导入器接口

```ts
interface Importer {
  format: string
  canHandle(extension: string, mimeType?: string): boolean
  import(source: ImportSource): Promise<ImportResult>
}
```

## 7.3 导出器接口

```ts
interface Exporter {
  format: string
  canHandle(format: string): boolean
  export(source: ExportSource): Promise<ExportResult>
}
```

## 7.4 插件注册中心

```ts
interface FormatPluginRegistry {
  getImporter(extension: string, mimeType?: string): Importer | null
  getExporter(format: string): Exporter | null
}
```

说明：

- 当前阶段使用静态注册即可
- 不需要动态安装与卸载

## 8. 0.0.2 首批实现范围

## 8.1 导入格式

### Markdown 导入

支持：

- `.md`
- `.markdown`

规则：

- 直接读取原文
- 做编码清洗
- 必要时补齐结尾换行

### Text 导入

支持：

- `.txt`

规则：

- 读取纯文本
- 清洗编码和换行
- 转成最保守的 Markdown
- 不强行猜复杂结构

## 8.2 导出格式

### Markdown 导出

规则：

- 原样输出 Markdown 文本
- 文件后缀为 `.md`

### Text 导出

规则：

- 基于 Markdown 去掉标记输出纯文本
- 文件后缀为 `.txt`

## 8.3 暂不进入首批的格式

- `pdf`
- `html`
- `docx`
- `long image`
- `share card`

说明：

- 这些格式要么依赖额外渲染能力，要么转换保真度不稳定
- 可以在后续版本按价值单独评估

## 9. Markdown 转换规则

## 9.1 Text -> Markdown

基础规则：

- 保留原始段落换行
- 多个连续空行压缩为最多两个
- 不自动推断复杂列表
- 如果首行明显像标题，可考虑转为一级标题

## 9.2 Markdown -> Text

基础规则：

- 去掉标题标记
- 去掉强调、代码、引用等语法符号
- 保留段落文本顺序
- 保留列表项文本内容

## 9.3 转换保真度策略

定义三档结果：

- `完整`
- `部分`
- `失败`

对于 `0.0.2`：

- `md` 导入导出应达到完整
- `txt` 导入导出应达到完整或接近完整

## 10. 错误处理策略

## 10.1 必须返回可解释错误

不能只返回空结果。

导入失败必须区分：

- 不支持的格式
- 文件读取失败
- 编码异常
- 内容为空

导出失败必须区分：

- 不支持的导出格式
- 内容为空
- 输出生成失败
- 文件写入失败

## 10.2 支持警告而不是一刀切失败

例如：

- 文本编码已自动修复
- 部分标记已丢失
- 标题使用默认文件名生成

这些应进入 `warnings`

## 11. 测试要求

## 11.1 样本文件

至少准备：

- 简单 Markdown 样本
- 含标题、列表、引用、代码的 Markdown 样本
- 普通文本样本
- 带多段换行的文本样本
- 空文件样本

## 11.2 单元测试关注点

- 格式识别是否准确
- `md` 导入结果是否保持原文
- `txt` 导入是否正确转 Markdown
- `md` 导出是否保持原文
- `txt` 导出是否正确去除 Markdown 标记
- 错误与警告是否符合预期

## 12. 与主工程的集成方式

## 12.1 ImportService

建议新增 `ImportService`，职责：

- 接受文件选择结果
- 调用格式插件导入
- 把 `ImportResult` 交给 `FileService` 创建文档

## 12.2 ExportService

建议扩展当前 `ExportService`，职责：

- 调用格式插件导出
- 生成真实文件
- 为系统分享提供输出结果

## 12.3 FileService

`FileService` 不应承担格式转换，只保留：

- 文档写入
- 文档读取
- 工作区归档
- 导出记录持久化

## 13. 后续扩展方向

在 `0.0.2` 完成后，可按价值继续扩展：

- HTML 导入
- HTML 导出
- DOCX 导入
- PDF 导出
- 长图导出
- 分享卡片导出

扩展前提：

- 不能破坏 Markdown 作为唯一内部标准格式的原则

## 14. 一句话结论

多格式能力应沉淀为一个独立的格式转换插件模块，以 Markdown 作为唯一内部标准格式，在 `0.0.2` 中先完成 `md/txt` 的导入导出闭环，再逐步扩展复杂格式。
